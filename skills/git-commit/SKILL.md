# DLAB5 Git Commit

The commit conventions on this workstation are **tacit** — there is no `CONTRIBUTING.md`, no `.gitmessage`, no `commit.template`, and no git hook anywhere. They exist only in the history, which is why they have to be written down here. The distinctive part is the **body**: DLAB5 commits explain *why*, carry a verification block with literal evidence, and end with two trailers.

Verified on: `DLAB5-W541-01`, git 2.43.0, gh 2.86.0, against `atmanyoga-fullstack` (4 commits), `digitalhome-cloud-darkfactory` (73), `dhc-digital-twin-demo` (2), `pc-configurations` (7), 2026-08-10; extended to the ERP-LAB-5 repos against `di-autohealer` (13), 2026-08-14.

## When to use this

- The user says "commit this", "commit and push", "open a PR", or "ship it".
- A chunk of work is finished and needs recording.
- You are about to write a commit message in any DLAB5 or ERP-LAB-5 repo.

## When NOT to use this

- **Amending or rewriting published history.** This skill only creates new commits. Never rebase or force-push a shared branch from here.
- **Merge commits.** All merges in these repos are default-generated by GitHub and carry no body and no trailers. Don't hand-edit them.
- **Deep secret scanning before a security-sensitive push** — that is `dhc-security-audit`, which greps full history for AWS keys, passwords, tokens and private keys. Step 3 below is only a staged-paths check.
- **Submodule pointer bumps on the DHC platform** — follow `dhc-amplify-gen2`'s "Verifying a backend change end-to-end" step 7, then come back here for the message.

## High-level flow

```
survey → identity → guard → subject → body → sign → commit → push → PR (only if needed)
   1         2         3        4       5       6       7        8         9
```

Steps 1–5 are read-only. Step 6 onward mutates state — do not start them until the message is written and the guards are clean. Step 9 is the exception rather than the rule: day-to-day work goes straight to `stage` and stops at step 8.

## 1. Survey the change

```bash
git status --short
git diff --stat
git diff --cached          # what is actually staged
```

The body has to explain *why* the change exists, which means reading it, not just listing filenames. If nothing is staged yet, stage deliberately — `git add -A` is fine for a coherent unit of work, but check what it swept up in step 3.

## 2. Identity guard

```bash
git config user.name
git config user.email
```

Expected: `Digital LAB 5` / `frankuwe.schwarz@gmail.com`.

**If `user.name` is literally the string `user.email`, stop.** That is a real copy-paste bug in `digitalhome-cloud-darkfactory` and `dhc-digital-twin-demo` — it has already mis-authored 58 of 73 darkfactory commits. Show it to the user and offer the fix:

```bash
git config user.name "Digital LAB 5"
```

Fix it going forward only. **Never rewrite existing history** to correct old authorship — these branches are shared, and the cost of a rewrite far exceeds a wrong name in a log.

## 3. Never-commit guard

Check the **staged paths** against the lists in `~/digitalhomeCloud/CLAUDE.md` and `~/digitalhomeCloud/digitalhome-cloud-darkfactory/CLAUDE.md`:

```bash
git diff --cached --name-only | grep -nE \
  'aws-exports\.js|\.env\.development|amplify_outputs\.json|\.amplify/|node_modules/|\.cache/|(^|/)public/'
```

Any output is a stop. Show the user what matched and why it is on the list; unstage only after they confirm. Silently unstaging hides a misconfigured `.gitignore`, which is the actual bug.

For a repo adopting Amplify Gen 2, also confirm `amplify_outputs.json`, `amplify_outputs.d.ts` and `.amplify/` are in `.gitignore` before the first backend commit.

In the **ERP-LAB-5** repos the never-commit list is different — the risk is
customer system data and oversized vendor archives rather than Amplify config:

```bash
git diff --cached --name-only | grep -nE \
  'scc\.conf$|sapcc-.*\.tar\.gz|sapmachine-jdk|\.trc$|ljs_trace.*\.log|samples\.csv|peers\.csv|api-raw\.jsonl|/output/|\.env$'
```

Trace logs and captures carry internal hostnames, subaccount ids and backend
system ids; the SCC distribution tarball is ~119 MB, above GitHub's 100 MB
per-file limit, and SAP-licensed. Also check nothing over 50 MB slipped in:

```bash
git diff --cached --name-only -z | xargs -0 -r du -h 2>/dev/null | sort -rh | head -5
```

This is a fast path check only. For history scanning, hand off to `dhc-security-audit`.

## 4. Pick the subject convention

Detect it from the repo, not from habit:

| Repo | Convention | Example |
|---|---|---|
| `atmanyoga-fullstack`, `digitalhome-cloud-darkfactory`, `dhc-digital-twin-demo` | `type(scope): lowercase imperative` | `feat(web): implement the design as a Gatsby site` |
| `pc-configurations` | `DEVICE: lowercase imperative` | `W541: pin NVIDIA 470 against transitional packages` |
| ERP-LAB-5: `di-autohealer`, `sap-cc-operator`, `darkfactory` | Bare **sentence-case imperative**, no prefix at all | `Add suspend and resume commands with an interactive flow walk` |

**Do not add a Conventional Commits prefix to an ERP-LAB-5 repo.** All 13
`di-autohealer` commits are prefix-free, capitalised, and read as a sentence
describing what the change does for the user — `Stop the table-name rule eating
ordinary words, mask the SLT prefix`, not `fix(rules): …`. Subjects there run
long by design and often name two related effects separated by a comma.

Rules that hold across all three:

- Imperative mood, **no trailing period**. Lowercase after the colon in the two
  prefixed conventions; sentence-case from the first word in ERP-LAB-5.
- Types actually in use are `feat`, `chore`, `docs`. Do not invent `fix`, `refactor`, `test`, `ci` or `!` breaking markers unless the change genuinely is one — a type nobody uses reads as noise.
- Scopes are lowercase single words matching a package or domain: `web`, `monorepo`, `core`, `edge`, `portal`, `weather`, `pipelines`, `skills`.
- **Subject length is not policed.** The house average is 55–69 characters and the longest is 103. Favour a clear subject over a truncated one.
- Submodule pointer bumps use an em dash: `chore: bump repos/core — cache:no-store fix for stale block-def loads`.

## 5. Write the body

This is the part that makes a DLAB5 commit recognisable. Median body is ~6 lines; a real change runs 27–62. Wrap prose at ~76–80 columns.

The recurring shape, in order:

1. **One or two prose paragraphs of context** — why this change exists, what problem it solves, what it replaces. Not a restatement of the diff.
2. **Labelled bullet blocks**, each introduced by a mini-heading ending in a colon, e.g. `Fixes in the existing scaffold that would have broken the build:` or `Submodule bumps:`. Bullets use `- `, never `*`. Two-space indent for sub-bullets.
3. **A verification block with literal evidence.** House openers: `Verified with …`, `Verified after reboot:`, `Verified live on stage.`, `Verified end-to-end against stage S3.`, `All three green on stage.` Indent command output two spaces:
   ```
   Verified after reboot:
     nvidia-smi -> Quadro K2100M, driver 470.256.02, CUDA 11.4
     dkms status -> nvidia/470.256.02, 6.8.0-106-generic: installed
   ```
4. **A closing caveat or status paragraph** where relevant — deployment state (`Local only; not pushed.`, `stage NOT pushed.`) or a deliberate trade-off with its reasoning.

Typography: em dashes and `->` / `→` arrows are used freely. Backticks are rare in bodies — paths and identifiers are written bare.

## 6. Sign off

Exactly these two lines, blank line before, **nothing after**:

```
Designed-by: D-LAB-5 <frankuwe.schwarz@gmail.com>
Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```

Two rules that are easy to get wrong:

- **`Co-Authored-By` uses a capital B.** This is deliberately *not* GitHub's canonical `Co-authored-by`, and it is what all 71 existing trailers use. Matching the house form keeps `git log --format=%(trailers)` filters working.
- **Never put `🤖 Generated with [Claude Code](...)` in a commit message.** It appears in zero commits across all four repos. It belongs in PR bodies only.

Track the model version to whichever model is writing — the trailer has moved 4.6 → 4.7 → 4.8 → 5 over time, and it is a record of what actually wrote the change.

## 7. Commit

Use a heredoc so paragraph structure survives. Stacked `-m` flags collapse the body.

```bash
git commit -F - <<'MSG'
feat(web): short imperative subject

Context paragraph explaining why, wrapped at about 76 columns so it
reads well in git log without a terminal-width dependency.

Labelled block if the change has parts:
- first point
- second point

Verified with <method>: <literal evidence>.

Designed-by: D-LAB-5 <frankuwe.schwarz@gmail.com>
Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
MSG
```

Quote the heredoc delimiter (`<<'MSG'`) so backticks and `$` in the body are not expanded by the shell.

## 8. Push

```bash
git branch --show-current
```

**Where the work belongs depends on whether the repo has a `stage` branch.**

| Repo | Working branch | Rule |
|---|---|---|
| `atmanyoga-fullstack`, `digitalhome-cloud-darkfactory`, `digitalhome-edge` | `stage` | Commit and push **straight to `stage`**. No topic branch, no PR. |
| `pc-configurations`, `dhc-digital-twin-demo` | `main` | Only `main` exists; commit directly, as the existing history does. |
| ERP-LAB-5: `di-autohealer`, `sap-cc-operator`, `darkfactory` | `main` | Only `main` exists; commit directly. No staging deploy hangs off these, so there is nothing for a `stage` branch to buy. |

```bash
git push origin stage
```

Routing every change through a topic branch and a PR only delays the staging deploy that tells you whether the change actually works. `stage` is what Amplify Hosting builds — getting there fast is the point.

**Never commit directly to `main` on a repo that has a `stage` branch.** `main` is production and is only ever updated by a promotion PR from `stage` (step 9). If you find yourself on `main` in one of those repos, switch:

```bash
git checkout stage && git pull --ff-only origin stage
```

Use a topic branch **only when you actively want review before the change reaches staging** — a risky migration, an auth or IAM change, anything a second pair of eyes should see first. Then branch as `<type>/<kebab-desc>`, reusing the Conventional type as the prefix (`feat/design-import`, `chore/skill-reuse`), and delete it once merged so the branch list stays at `main` + `stage` plus whatever is genuinely in flight:

```bash
gh pr merge --delete-branch          # or: git push origin --delete <branch>
git remote prune origin
```

Only push when the user asked for it. A commit is cheap to amend locally; a push is not.

## 9. Open a PR

There are only two reasons to open one.

**Promotion, `stage` → `main`.** This is the normal path to production:

```bash
gh pr create --base main --head stage --title "<title>" --body "$(cat <<'BODY'
...
BODY
)"
```

**A topic branch you deliberately created** under the review exception in step 8 — base it on `stage`, not `main`, or it bypasses staging entirely.

Before opening a promotion PR, check there is actually something to promote:

```bash
git rev-list --count origin/main..origin/stage
```

PR bodies may carry the Claude Code attribution line; commit messages may not. Repeat the verification evidence in the body — it is what a reviewer reads first.

## Verify

After committing, confirm the message came out right:

```bash
git log -1 --format=%B
git log -1 --format='%(trailers:key=Designed-by)%(trailers:key=Co-Authored-By)'
git log -1 --format='%an <%ae>'          # expect: Digital LAB 5 <frankuwe.schwarz@gmail.com>
```

Both trailers must appear, the author must not be `user.email`, and `git log -1 --format=%B | grep -c '🤖'` must be `0`.

Two known-good commits to compare shape against:

```bash
git -C ~/DLAB5/atmanyoga-fullstack log -1 --format=%B 504a39e   # Conventional + verification block
git -C ~/pc-configurations        log -1 --format=%B 57e33b4    # device prefix + caveat paragraph
```

## Troubleshooting

### Symptom: `gh pr create` fails with "no commits between stage and <branch>"
The branch was created but the commit landed on the previous branch, or the push didn't include it. Check `git log --oneline stage..HEAD`.

### Symptom: a topic-branch PR was opened against `main` instead of `stage`
Close it and re-open with `--base stage`. Merging a feature to `main` directly skips the staging deploy that Amplify Hosting builds from. A `--base main` PR is correct only for a `stage` → `main` promotion.

### Symptom: work was committed to a topic branch when it should have gone to `stage`
If it is not yet pushed, `git checkout stage && git cherry-pick <sha>` and delete the branch. If it is pushed, just open the PR against `stage` and merge it — the result is identical, only slower.

### Symptom: author shows as `user.email <frankuwe.schwarz@gmail.com>`
Step 2 was skipped. Fix the config, then `git commit --amend --reset-author` — but **only if the commit is not yet pushed**. If it is, leave it; a wrong name in the log is not worth a shared-history rewrite.

### Symptom: the body lost its paragraphs and became one line
`-m` flags were used instead of a heredoc. `git commit --amend -F -` with the full message, before pushing.

### Symptom: `git commit` opens an editor and hangs
No `-F`/`-m` was supplied. Interactive editors are unavailable in this environment — always pass the message via heredoc.
